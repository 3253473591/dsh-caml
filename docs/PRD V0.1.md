# PRD：DSH 记忆冲突可验收层

> 文档状态：草稿 v0.1 ｜ 日期：2026-11-08
> 本文档为**骨架版**，标注 `【待扩展】` 的章节由你后续细化，其余章节为已确认的共识内容。

---

## 1. 背景与问题

### 1.1 现状
DeepSeek Harness（DSH）采用 Cordis 微内核，记忆层可以以独立插件形式挂载。社区已有 `dsh-memory`、`dsh-mnemon`、`meow-memory`、`dsh-peoplememory` 等记忆插件，覆盖了存储、召回、分层编排等基础能力。

### 1.2 核心问题：记忆冲突静默累积
现有记忆插件对**冲突处理**普遍缺位或简化：

- **`Mem0 OSS v3`**：抽取管线变为 ADD-only，`add()` 不再发出 UPDATE/DELETE，新旧矛盾事实同时累积。
- **`dsh-memory`**：明确声明“不做冲突裁决”，冲突检测仅靠 topic 等值与字符串比较。
- **`dsh-memory-beta`**：承认记错后“会每轮重复错误且看起来正常”，缓解手段只是注入一句“以用户当前说法为准”。
- **`dsh-peoplememory`**：设计意图是“保留两版并标记置信度”，但项目仍处于 scaffold 阶段。

结果是：**时间敏感事实（当前雇主、当前城市、当前负责人、当前偏好）在被新信息推翻后，旧值不会被可靠地降级或取代，召回时可能给出过时答案。**

### 1.3 为什么这个 Demo 值得做
不是“再做一个记忆插件”，而是**把冲突裁决从隐式行为变成显式契约，并让这个契约可以被自动评测**。这是一个边界清晰、可严格验收的工程问题，比“做一个带记忆的求职 Agent”更适合作为应届生求职作品。

---

## 2. 产品定位

### 2.1 一句话定义
**一个面向 DSH 的记忆层插件：对可变状态事实的冲突给出显式裁决语义，并附带可自动跑分的冲突评测集。**

### 2.2 目标用户
- **直接用户**：加载本插件的 DSH Agent 开发者（任意垂直领域）。
- **演示用户**：求职场景下的应届生本人（作为三个验证场景之一）。

### 2.3 与现有 DSH 记忆插件的差异

| 维度 | 现有插件 | CAML |
|---|---|---|
| 冲突处理 | 不做裁决 / 仅字符串比较 / 仅提示词缓解 | **显式裁决策略 + 可观察结果** |
| 旧事实处置 | 覆盖或共存 | **保留于审计轨迹，默认不召回** |
| 可验证性 | 以功能演示为主 | **自带冲突评测集与通过标准** |
| 业务绑定 | 通用但无裁决 | 通用裁决层，求职/企业/旅游为验证场景 |

## 3. 核心概念

### 3.1 记忆分层（本 PRD 范围内）
- **短期记忆**：当前会话内的工作上下文（沿用 DSH 会话机制，不在本插件重点内）。
- **长期记忆**：跨会话持久化的事实，本插件的核心管理对象。

### 3.2 冲突的定义
同一 `(subject, predicate)` 下，存在多条“当前有效”的事实，且 object 不一致，即视为冲突候选。

### 3.3 三类裁决语义（本版本支持范围）

| 类型 | 语义 | 典型场景 | 期望行为 |
|---|---|---|---|
| **A. 取代（Supersede）** | 新事实取代旧事实成为当前有效值 | 求职地变更、当前雇主变更 | 新值进入默认召回；旧值标记 `superseded`，默认不召回，审计可查 |
| **B. 版本化转移（Versioned Transfer）** | 角色/关系发生转移，需保留双方时间线 | 企业 Agent 中人事变更 | 问“现在谁负责”得新值；问“之前谁负责”得旧值 |
| **C. 加权衰减（Weighted Decay）** | 偏好漂移而非事实矛盾，旧偏好降权而非删除 | 旅游推荐中偏好演化 | 推荐以新偏好为主；被问“以前喜欢什么”时仍可召回旧偏好 |

> **明确不做**：多模态记忆、图数据库、真正的 MoE 专家路由（仅在叙事中提及“意图路由借鉴 MoE 分工思想”）。

## 4. 功能需求

### FR-1 记忆写入与冲突检测
- 提供 `remember(subject, predicate, object, metadata)` 接口。
- 写入时检测同 `(subject, predicate)` 下是否存在当前有效事实。
- 若存在且 object 不一致，触发裁决流程，按配置的策略选择 A/B/C。
- 若不存在冲突，直接写入为当前有效事实。

### FR-2 三类裁决策略
- 策略 A：关闭旧事实的 `valid_until`，设置 `superseded_by` 指向新事实。
- 策略 B：旧事实保留完整时间窗，新事实开启新时间窗，二者通过 `relation` 字段关联。
- 策略 C：旧事实降低 `weight`（可配置衰减系数），新事实以默认权重写入；不关闭旧事实时间窗。
- 裁决策略可按 `predicate` 类型配置（如 `location` → A，`role` → B，`preference` → C）。

### FR-3 召回
- **默认召回**：仅返回满足 `valid_until is null`（或覆盖当前查询时间）且 `weight` 高于阈值的记录。
- **审计召回**：提供 `audit(subject, predicate)`，返回完整时间线与裁决记录，供“以前是什么”类查询使用。
- 召回结果需附带 `status` 字段（active / superseded / decayed），供上层 Agent 判断。

### FR-4 工具注册
通过 DSH `ctx` 注册以下工具，供任意 Agent 调用：
- `remember`：写入记忆
- `recall`：默认召回
- `audit`：审计召回
- （可选）`resolve_conflict`：当策略判定为“待确认”时，交由上层决策

### FR-5 插件配置
- 裁决策略映射表（predicate → 策略）
- 衰减系数、权重阈值
- 存储后端选择（默认 SQLite，预留接口）

## 5. 非功能需求

- **依赖最小化**：v1 不引入向量库；召回基于结构化字段过滤 + 关键词匹配。
- **可观测性**：每次裁决产生一条可读的裁决日志（谁被谁取代、何时、依据哪条策略）。
- **延迟**：单次 `remember` / `recall` 在本地 SQLite 下应低于可接受阈值（具体数值 `【待扩展】`）。
- **可移植性**：不绑定具体 LLM，裁决逻辑不依赖模型调用（可选：用 LLM 做冲突候选预筛，但需可关闭）。

## 6. 验收标准

### 6.1 功能验收
- 三类裁决语义各自在对应场景下产生预期状态迁移。
- 默认召回不返回被取代/被衰减至阈值下的旧事实。
- 审计召回能还原完整时间线。

### 6.2 评测集设计 `【待扩展】`
> 建议结构：3 类语义 × 每类 3～5 条用例，每条用例包含：初始记忆、触发写入、查询问题、期望召回结果、期望审计结果、判定方式（自动/半自动）。

### 6.3 通过标准 `【待扩展】`
> 建议：每条用例有明确的 pass/fail 判定规则；README 中给出通过率与失败案例归类。

### 6.4 场景覆盖（验证用）
- 求职场景：求职地变更、目标岗位变更
- 企业场景：项目负责人变更
- 旅游场景：旅行偏好演化

## 8. 测试计划 `【待扩展】`

> 本节由你细化。骨架建议：

- **单元测试**：每类裁决策略的状态迁移正确性。
- **集成测试**：写入 → 裁决 → 默认召回 / 审计召回的端到端链路。
- **评测集回归**：6.2 的用例集作为回归基线。
- **反例测试**：不该召回的旧事实确实未被召回；不该覆盖的场景未被误覆盖。
- **DSH 插件加载测试**：在最小 Agent 中挂载插件并调用工具。

## 10. 风险与不做的事

- **风险**：DSH 插件规范若有变动，封装层需适配 → 缓解：裁决核心与插件封装解耦。
- **风险**：评测集规模小导致说服力不足 → 缓解：在 README 中诚实说明规模，并强调“可扩展的评测框架”本身是交付物。
- **不做**：向量库、图数据库、真 MoE 路由、多模态、生产级高可用。

## 11. 面试叙事（演示脚本要点）

1. **问题**：现有记忆插件对时间敏感事实的冲突普遍不做裁决，旧值会静默累积。
2. **主张**：把冲突裁决变成显式契约 + 可自动评测。
3. **演示**：同一套插件加载到求职 / 企业 / 旅游三个 Agent，分别展示 A/B/C 三类裁决。
4. **证据**：评测集通过率 + 失败案例归类 + 审计轨迹截图。
5. **边界**：明确说明 v1 不做什么，以及为什么这样取舍。
