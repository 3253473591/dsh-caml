# 评测扩展设计：提示词变体（PV）与记忆/上下文消融（AB）

> 日期：2026-11-16 ｜ 性质：设计稿（**未实现**）｜ 关联：[调研备忘](./2026-11-16-memory-hit-rate.md)、[06 测试](../06-test-plan.md)、[07 验收](../07-acceptance.md)

## 1. 目的与非目标

**目的**：回答两个当前 16 条用例回答不了的问题——

1. 模型在**真实措辞**下会不会调记忆工具、调得对不对？（PV）
2. 回答正确里有多少来自插件、多少来自对话上下文？（AB）

**非目标**：不做长上下文容量测试；不引入 LLM 当裁判；不改动 16 条确定性用例与 AC-11；不覆盖采集/遗忘/人格。

## 2. 两套评测

### PV：提示词变体（Prompt Variants）

同一场景，四种问法，各跑一次：

| 类 | 代码 | 例子（库：上海 active，杭州 superseded） | 期望行为 |
|---|---|---|---|
| 直接 | `direct` | "我现在想去哪个城市？" | 调 `caml-recall`，答上海 |
| 拐弯抹角 | `indirect` | "下周去面试，通勤怎么安排？" | 先召回当前城市，再据此回答 |
| 正确记忆但错误内容 | `contradict` | "我记得是杭州吧？" | 不盲从，指出库里是上海 |
| 完全无关 | `absent` | "帮我写个快排" | **不调**记忆工具，不编造 |

### AB：记忆/上下文消融（Ablation）

每个场景两种会话形态，问同一句 `direct` 问题：

| 形态 | 代码 | 含义 |
|---|---|---|
| 同会话 | `same` | 事实是在**本会话**里写入的，对话历史里已有 |
| 全新会话 | `fresh` | 事实在别的会话写入，当前会话零上下文，只能靠工具 |

**消融增益** `AG = accuracy(fresh) / accuracy(same)`。若 `fresh` 明显低于 `same`，说明模型在靠上下文而不是插件——这正是我们实际踩过的坑。

## 3. 用例格式

沿用现有 `eval/cases.json` 的写入字段，外加问法与判定：

```jsonc
{
  "id": "PV-A-01-direct",
  "suite": "pv",              // pv | ab
  "scenario": "求职-城市",     // 12 个场景之一
  "promptClass": "direct",    // direct | indirect | contradict | absent
  "session": "fresh",         // same | fresh
  "given": [
    { "subject": "我", "predicate": "目标城市", "object": "杭州", "observedAt": "2026-10-01T00:00:00Z" },
    { "subject": "我", "predicate": "目标城市", "object": "上海", "observedAt": "2026-11-01T00:00:00Z" }
  ],
  "prompt": "我现在想去哪个城市？",
  "expect": {
    "tools": {
      "mustCall": ["caml-recall"],
      "mustNotCall": [],
      "args": { "subject": "我", "predicate": "目标城市" }
    },
    "answer": { "mustMention": ["上海"], "mustNotMention": ["杭州"] },
    "rubric": { "2": "明确答上海且未提杭州", "1": "答上海但夹带杭州作当前值", "0": "答杭州/说不确定" }
  }
}
```

- `args` 只做**包含性**断言（不要求逐字段相等），避免过度约束模型。
- `absent` 类没有 `given`；`mustNotCall` 为三个工具全部。

## 4. 运行协议

- 每个 case 一个新库；`same` 形态先在同一会话写入事实再提问；`fresh` 形态写入后**销毁会话**，新建会话提问。
- 固定模型与温度（记录模型 id、版本、温度；模型升级视为新基线）。
- 每条 case 跑 1 次；争议 case 重跑 2 次取多数，并记录波动。
- **不把上一次的输出放进下一次的上下文**。

## 5. 指标（分母写死，避免自欺）

| 指标 | 定义 | 分母 |
|---|---|---|
| 工具命中率 `THR` | 该调且调对（工具名 + 关键参数包含） | 应调用 case 数 |
| 误调率 `FTR` | 不该调却调了 | 应不调用 case 数（`absent`） |
| 回答正确率 `AA` | rubric=2 的占比 | 全部 case |
| 旧值泄漏率 `SLR` | 回答把 `superseded` 值当当前值的占比 | 有旧值的 case 数 |
| 编造率 `FR` | `absent` 组出现具体记忆事实的占比 | `absent` case 数 |
| 消融增益 `AG` | `AA(fresh)` 与 `AA(same)` 的差 | 每场景 |
| 人工分歧率 | 双评不一致占比 | 抽检样本 |

## 6. 判定协议（两段式）

1. **工具段（确定性）**：断言调用了哪些工具、参数是否包含关键值；可完全自动化。
2. **回答段（rubric）**：0/1/2 三档，双人独立评；抽检 20%，分歧由第三人裁决。
   **禁止**仅用 LLM 打分作为结论；LLM 打分只允许作为"预筛"，最终以人工为准。

## 7. 规模与成本

| 套件 | 用例 | 每 case 模型调用 | 总计 |
|---|---:|---:|---:|
| PV | 12 场景 × 4 类 = 48 | 1–2 | ~72 |
| AB | 12 场景 × 2 形态 = 24 | 1–2 | ~36 |
| 合计 | 72 | — | ~108 次调用 + 人工评审约 2 小时 |

## 8. 与现有评测/验收的关系

- 16 条 `ET-*` **保留**，继续作为确定性核心（AC-11 不变）。
- PV/AB 是**附加证据**，失败不直接判 AC 不通过，但要写进 README 的"已知限制"。
- v1.1 的目标阈值（非 gate）：`direct/indirect` 的 `THR ≥ 90%`、`absent` 的 `FR = 0`、`SLR = 0`、`AG ≥ 0.6`。

## 9. 风险

| 风险 | 缓解 |
|---|---|
| 模型升级导致数字漂移 | 记录模型与温度；换模型即新基线，不混比 |
| 提示词泄漏（case 里写了期望值） | 评分人只看回答与库，不看 case 期望 |
| 人工评审偏差 | 双评 + 20% 抽检 + rubric 写死 |
| 拐弯抹角类本身有歧义 | 先手工跑 12 条探针，删掉歧义过大的问法 |
